# Fly Over Slime — BACKEND (game server, carried over from Bowling Roll)

Frontend (3D client) lives at `../Fly-over-slime`. Colyseus + Mongo, ported from `C:\ThreeJS\Kayak-and-surf\Kayak-and-surf -backend`.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp })`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- The server's Mongo doc is a signed-in player's real save; the client keeps a localStorage cache that the server's copy replaces on load (`progress`), or that becomes the first save on `noProgress` unless the cache belongs to another account (client `net.js`, `state.js` owner key). A guest's progress lasts the browser cache only.
- Messages client -> server: `saveProgress` (the whole `state` snapshot + `level`, throttled client-side), `identify` (`{ userId, username, pfp }` after a sign-in/out mid-session), and presence: `pose`, `loadout`, `setAvatar` (below). Server -> client (private): `progress` (the saved doc, sanitized), `noProgress` (new account, guest, or no database), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted. Roster (`PlayerState`): `username`, `signedIn`, `pfp` plus the presence fields.
- Saved progress shape (`PlayerDoc`, client `src/state.js` `snapshot()`): `wins`, `skill`, `bestSkill` (`$max`), `totalSkill`, `level`, `rebirths`, `tokens`, `slingshots`/`equippedSling`, `platforms`, `pets[] { uid, id, tier: ''|'g'|'d', equipped }`, `nextUid`, `discovered[]` (pet id + optional `:g`/`:d`), `indexClaims`, `trails`/`trail` ("" = none; the equipped id must be owned), `passes`, `extraSlots`, `storageBuys`, `hatchMax` (1..`HATCH_MAX`), `autoRebirth`, `autoFly`, `playTime`, `flights`, `bestDistance` (`$max`), `chestAt`, `potions`, `boostLeft`, `daily { unlocked, last, claimed[] }` (client-local days, not server-authoritative), `title`, `stats`, `settings`, `lastSeen`. `sanitize.ts` only bounds shapes; the old boats/engines/partners/race/spin/daily server logic is gone.
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): the client plaza's four boards. Top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`bestSkill`, `playTime`, `level`, `wins`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS`. `connectDb` creates a descending index per stat.
- Presence (`src/presence.ts`, `test/Presence.test.ts`): what the others draw in the world (client `remotePlayers.js`), relayed through the roster as sent, only bounded. Roster fields `x`/`y`/`z` (feet, m), `yaw` (wrapped to -PI..PI), `speed`, `vy`, `grounded` (drive the run/jump/land animation), `flying`, `pitch`/`roll` (flight somersault + bank), `training` (slingshot pull), `sling`/`trail`/`title` (catalog ids matching `ID_PATTERN`, "" = none), `pets` ("id,id:g,id:d", at most `PRESENCE_PETS_MAX`), `avatar` (Bloxity look JSON `{ equipped, proportions, skin }`, at most `AVATAR_MAX_LEN`, never parsed). Messages `pose`, `loadout` { sling, trail, title, pets: [{ id, tier }] }, `setAvatar` { avatar }; the join options may carry `pose`, `loadout` and `avatar` too.
- **Bloxity** (`src/bloxity.ts`, `src/legion-room-reporter.ts`, `test/Bloxity.test.ts`; docs.bloxity.io/#html5, hosting.bloxity.io/docs): with `BLOXITY_API_URL` set (deployed) a player's account is ONLY the `user._id` of the join / `identify` option `token`, verified at `POST /v1/auth/game-token/verify` (`identifyFrom`; a bad token = guest; a client-sent `userId` is ignored; an `identify` without `token`/`userId` keeps the account); locally (unset) the client's `userId` is used. Hosted leaderboards: every `LB_REPORT_EVERY_MS` (and when a player leaves / the room closes) the changed scores of `LB_BOARDS` (level, skill = bestSkill, wins, distance = bestDistance, rebirths; read from the stored save, `scoresFromDoc`) go to `/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report` (needs `BLOXITY_REPORT_TOKEN`; ids as `legion_<id>`); the client `bloxity.js` `LEADERBOARDS` must declare the same ids. `installRoomReporter()` (called after `listen` in `index.ts`) pushes this pod's rooms to the matchmaker every 2 s (`started` must stay false: a started room is listed LOCKED and hidden from Open Rooms / the ESC server list; `test/RoomReporter.test.ts`; check `https://api.bloxity.io/v1/games/fly-over-slime/rooms` shows `locked:false`) (`BLOXITY_REPORT_TOKEN` + `MATCHMAKER_REPORT_URL` + `BLOXITY_GAME_ID`; a no-op locally) so the game page's Open Rooms list and friends' invites find them. Game stats (profile + missions, `reportStats`): every `STATS_REPORT_EVERY_MS` (60 s, and on leave / room close) the changed values of `STAT_DEFS` (level, best_skill, wins, rebirths, best_distance, flights, eggs_hatched, pets_owned, chests_opened, play_time; read from the stored save by `statsFromDoc`, whole numbers) go to `POST /v1/games/{BLOXITY_GAME_ID}/stats` as `{ definitions, players: [{ userId: legion_<id>, values }] }` (<= 200 players a call, same env vars as the boards). Bloxity keeps a high-water mark that can never be lowered and REJECTS values above a type's ceiling, so values are clamped to `STAT_CEILING`. Roster extras: `uid` (verified account id, for chat bubbles) and `emote`/`emoteAt` (`emote` { id }, server ms; "" stops).
- Invites (`src/invite.ts`, `test/Invite.test.ts`; they earn the client's Friend Boost, +10% Skill gain per friend who JOINED, `FRIEND_BOOST` in the client `config.js`): `invite` { joined, sent, guest? } goes to the player after each load (`inviteRefresh` re-reads it) and answers `invited` { friendId } (a direct Bloxity invite, kept in `invitesSent`). A SIGNED-IN player who joins through an inviter's link (`ref` join option = the link's tag) or after the inviter's direct invite credits that inviter once ever: `invitedBy` is set with a conditional write (so two rooms/pods can't both credit), the inviter's `invites` goes up with `$inc`, and an online inviter gets live `invite` + `friendJoined` { name } (the friend gets `invitedBy` { name }). Server-written only, never by `saveProgress`; guests are never credited.
- `src/constants.ts` bounds must cover the client's `src/config.js` (catalog ids match `ID_PATTERN`, incl. engine `ladder-N`; currency up to ~3.6e28). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (keep it 2-100 for party play; no `seatCap`: the matchmaker sizes pods). Needs repo var/secret `LEGION_GAME_ID` (= `fly-over-slime`) and secret `LEGION_DEPLOY_TOKEN`.
